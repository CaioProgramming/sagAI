# Character Levels, Prestige & Legacy — Plan

Status: **brainstorm closed, not implemented.** Applies to **new sagas only**; existing sagas never get the feature. Implementation starts after the feature currently being closed ships. **Android only first**; KMP/iOS comes much later, once Android is validated end to end. The blueprints and the RC config are drafted in `blueprints/` (ready to publish through the CLI).

## Goal

Every character (the player included) has a level from 1 to 100 that **constrains the story**, not just decorates it.
The level is earned through **feats**: moments that changed something in the story and cost the character something.
Level is never granted by the AI directly, never by volume of play, and never only for action: a hard conversation,
leaving an ally behind, confessing a love or a sacrifice weigh as much as a duel.

Two things sit on top of the level, both generated by the AI from the feat log and both shown as profile "charm"
(Steam/Discord-style: title, frame, accent, badge). **No image generation.**

| Layer | Question it answers | Window | Nature |
|---|---|---|---|
| Level / XP | How much did they *grow*? | per event | accumulates (the feat ledger) |
| Prestige (medal) | Which deeds of this chapter deserve to be remembered? | per chapter, one deed per medal | AI-judged from the feat log, a coin |
| Legacy (title) | Did they *change the story* this act? | per act | permanent, few per act |

## Principles

1. **The AI classifies, the code computes.** The AI writes the feat and picks a tier from a small ordinal scale; XP,
   level and caps are computed in code from Remote Config tables. The AI never outputs a number that becomes XP.
2. **Impact over action.** The tier measures *what changed* and *what it cost*, identical for every genre and every kind of feat.
3. **Level is a story constraint.** The reply prompt receives a pre-digested power directive. A lvl 30 player against a
   lvl 15 thug wins plainly; the AI does not invent difficulty.
4. **Everything is explainable.** Each feat stores `changed` and `cost`; the player reads in the log exactly why it
   paid X XP or nothing.
5. **Remote-only config.** Curve, tier table, caps, gap bands: all in RC, no compiled fallbacks (if unset, the feature is off).
6. **Wrap every AI call in `RequestResult`** (`executeRequest` + failure path). A failed evaluation never breaks the lore update.

## Decision: new post-request, not a field on `UnifiedLoreUpdate`

`UnifiedLoreUpdate` (`event` + `charactersUpdates` + `wikiUpdates` + `locationUpdates`) is produced by one **HIGH** call
fed with wide context (contextual history, the last `LORE_UPDATE_LIMIT` events, last messages, all characters, all wikis).
It already does four jobs. Recommendation: **a separate `character_feat_evaluation` request, run right after it.**

| Concern | Inside Unified | Separate post-request |
|---|---|---|
| Attention | rubric competes with 4 other tasks | one job, rubric front and center |
| Input | wide (world-level) | narrow: this event + participants only; fewer tokens than it sounds |
| Evidence | generated in the same breath, cannot be cross-checked | runs *after* `RelationshipUpdateEvent` rows exist, so a feat can cite one |
| Failure | a bad `feats` field fails the whole HIGH lore call | isolated; lore already saved; retry by `timelineId` |
| Tuning | every rubric tweak touches the lore blueprint | publish/test the rubric on its own |
| Cost | 0 extra calls | +1 call per event, small prompt, tier tunable (start MEDIUM, test HIGH on the calibration set) |

Your instinct was right: the judgement is character-focused and needs validation the world-level call is not built for.

Integration point: `TimelineUseCaseImpl`. The `Unified` body is duplicated in `generateFullLoreUpdate` and in the
`Success` branch of `generateFullLoreUpdateStream`, which are the funnel for all callers (`SagaContentManagerImpl`,
`NarrativeActionExecutorImpl`, `SagaDetailUseCaseImpl`, `LoreDebugViewModel`). Call one new
`CharacterProgressionUseCase.evaluateEvent(saga, timeline)` from both, **after** `updateCharactersFromLore`.
Gated by `Saga.progressionEnabled` and the RC kill switch.

## Data model (additive migration, new version; never edit an existing migration)

- `Saga`: `progressionEnabled: Boolean` (default false; true only for sagas created after release). There is **no per-saga power scale**: the cap is a fixed 1 to 100 and the meaning of a level comes from the saga's own roster (see blueprint 1).
- Generation flags, one boolean each, meaning *the last generation succeeded* (not *a log exists*): `Timeline.experienceGenerated`, `Chapter.honorsGenerated`, `Act.legacyGenerated`. Default false on creation of the item; set true only when the call returns successfully, even with zero feats or zero honors. They drive the review described in "Review when a generation failed".
- `Character`: `baseLevel: Int?`, `levelRationale: String?`, `skills: List<String>` (new column; **replaces `Abilities` for new sagas**, see the decisions below; the old `Abilities` columns are never dropped and only old sagas use them).
- `Character` (status, independent of progression, see "Character status"): `status: CharacterStatus?` (null = ACTIVE), `statusNote: String?`, `statusTimelineId: Int?`.
- New table `CharacterFeat`: `id`, `characterId`, `sagaId`, `timelineId`, `kind`, `title`, `changed`, `cost`, `tier`, `xp` (frozen at write), `relationshipUpdateEventId?`, `createdAt`. Unique per `(characterId, timelineId, ordinal)` so re-running an event replaces its feats (idempotent).
- Level is **derived**: `baseLevel` + level reached by `SUM(xp)` against the RC curve (DAO sum, no stale cached column).
- New table `CharacterHonor`: `id`, `characterId`, `kind` (MEDAL | TITLE), `scopeId` (chapterId or actId), `name`, `emoji` (medals only), `description` (the reason for a medal, the epitaph-like legend for a title), `featIds`, `posthumous: Boolean` (copied from `status == DEAD` when granted).

## Level math (RC `character_progression`, pure Kotlin, no Android deps so it can move to KMP)

- `LEVEL_XP`: cumulative XP to reach level N (formula params `XP_BASE`, `XP_EXPONENT`, or an explicit array).
- `TIER_XP`: tier 0 to 5 mapped to XP. Independent of `kind`.
- Calibration target: a full saga (~3 acts, ~5 events/chapter) of mostly tier 3-4 feats moves the player ~+40 levels. Simulate on real events before publishing.
- `PLAYER_START_LEVEL_CAP` (e.g. 25) so the protagonist always has room to grow; NPCs and villains have no cap.

### Impact tiers (the rubric, same for all genres)

| Tier | Meaning | `changed` | `cost` |
|---|---|---|---|
| 0 | Took part, nothing moved | required (why nothing) | none |
| 1 | Striking scene, nothing different after | optional | none |
| 2 | Changes a relationship or state | required | optional |
| 3 | Costs something, becomes an arc beat | required | required |
| 4 | Changes the chapter's direction | required, persistent | required, real |
| 5 | Changes the act or saga | required, persistent | required, heavy |

Examples: hard talk that opens a wound = 2-3; confessing love = 3-4; leaving an ally behind for a greater good = 4;
sacrificing oneself = 5. Code guards: tier ≥ 3 needs a non-empty `cost`; tier ≥ 4 needs a `changed` that names something persistent. Violations are clamped down, never up.

### Anti-farming (all in code)

1. Events come from story progress, not per message: spamming chat creates no feats.
2. A feat counts only if something is different afterward (`changed` rule above).
3. Repeated `kind` inside one chapter decays: 100% → 60% → 30% (`REPEAT_DECAY`).
4. Per-event and per-chapter XP caps as a fraction of the current level's threshold (`EVENT_XP_CAP_PCT`, `CHAPTER_XP_CAP_PCT`).
5. Safety net, off until tests show inflation: a multiplier for contested feats by level gap (`CONTEST_GAP_MULTIPLIER`). The cost axis should already collapse a lvl 30 vs lvl 15 fight to tier 1/0.

## Blueprints (all RC, `_blueprint` suffix, atomic SCREAMING_SNAKE_CASE entries, no `template`)

Drafts ready to publish through the CLI at implementation time, in `blueprints/`: `character_feat_evaluation_blueprint.json`, `character_honors_blueprint.json`, `blueprint_additions.json` (additions to `character_generation_blueprint`, `unified_lore_generation_blueprint` and `reply_generation_blueprint`) and `character_progression.json` (the RC config; every number is a placeholder for phase 0).

### 1. Level bands, no per-saga scale (decided)
A saga does not start with its limits defined; development defines them. So there is **no scale generated at saga creation**. The cap is a fixed 1 to 100, and the meaning of a level comes from two things: a universal set of **bands** in RC (`LEVEL_BANDS`: ordinary, trained, veteran, elite, legendary, mythic) used as the first reference and as the labels in the power directive, and, as the story grows, **the saga's own roster**: a new character is placed relative to the characters already in the saga (see blueprint 2). The early characters (the player and the first NPCs) are placed against the bands alone; later ones against the roster too. Nothing here needs a new AI call or a field on `Saga`.

### 2. Placement: extend `character_generation_blueprint` (fields `baseLevel`, `levelRationale`)
Input: the character's backstory, the universal `LEVEL_BANDS` and the **roster** (the saga's existing characters with their current level and a short role, so the new level is relative to what the saga already established). Output: `baseLevel`, a one-line `levelRationale` and the initial `skills[]` (which replaces the abilities text fields). Drafted in `blueprints/blueprint_additions.json` (`character_generation_blueprint`).
Runs for the player's character and for mid-story NPCs, since both go through this blueprint. The villain revealed in act 2 can enter at 100.
Code clamps the player to `PLAYER_START_LEVEL_CAP`.

### 3. Feat evaluation: NEW `character_feat_evaluation_blueprint` (the core)
- **Input (args):** the completed event (`content` + its messages), participants only with their current `level`, top `skills`, last N feats
  (to spot repetition), the universal `LEVEL_BANDS`, the `RelationshipUpdateEvent`s of this `timelineId` as evidence, and each participant's opponent levels in the scene.
- **Output per participant:** `feats[]` of `{ kind, title, changed, cost, tier, relationshipEvidence? }` plus `newSkills[]`. Tier 0 is allowed with a reason, only for participants who were relevant to the event, so the player can read why nothing paid.
- **Directives:** CHANGED_AND_COST (the two fields are the proof), IMPACT_NOT_ACTION (kinds: bond, sacrifice, vulnerability, moral choice, discovery, overcoming, leadership: none is lesser), PRESENCE_MATTERS (a protagonist locked away while the story follows others earns little), LEVEL_ONLY_FOR_CALIBRATION (use levels to judge risk, never to inflate), SAME_LANGUAGE_AS_SAGA, ONLY_WHAT_HAPPENED.
- **Never outputs XP.** Code maps tier to XP and applies decay/caps. Skills are appended and deduped, capped by RC `MAX_SKILLS`.

### 4. Honors: NEW `character_honors_blueprint` (medal and title, scope arg)
**The AI judges, code guards** (the same split as XP: the AI classifies, the code bounds). At chapter and act close the honors call reads the structured feat log, decides **who, if anyone, earned a medal or a legacy**, and names it. Code does not elect anyone.
- **Input:** chapter close: every participant's feats of that chapter (title, kind, tier, `changed`/`cost`, XP) and their current level, plus the genre and chapter title. Act close: the act's feats grouped by character, the medals already granted in the act, the act's continuity summary and title. No transcript.
- **Instructions:** honors are rare and **zero is a normal answer**; at most one legacy per character per act. A medal recognizes **one distinct deed**: a feat of this chapter (or a tight group of related feats) that deserves to be remembered. Do not bundle unrelated deeds into one medal, do not split one deed into several, and each feat backs at most one medal, so a chapter in which a character saved someone, fought and then sacrificed yields separate medals and no important feat is left behind (presence still counts: a protagonist locked away while the story follows others earns none); a legacy means they changed the story of the act, with the same impact rule used for chapters and events (what changed, what it cost).
- **Output:** `honors[]`, possibly empty, each citing the `featRefs` that justify it.
- **Code guardrails (validation, not election):** validate references **by id, never by text**: each feat enters the prompt with its `CharacterFeat.id` and the AI returns `featRefs` as a list of ids only. Drop a reference that is not an id of the input, whose feat does not belong to the honor's character, or that is outside the chapter/act scope; drop the honor if no valid reference remains (`toAINormalize`/`normalizetoAIItems` exclude nothing by default, only `$stable` and `companion`; the *caller* passes the exclusion list, so the feat items for this call must simply not list `id` in it. Strings are truncated at 500 chars by the normalizer, which is enough for `changed`/`cost` and titles). The prose (name, reason, title, description) is free and is not verified in code; it is kept honest by feeding only structured feats (no transcript), telling the AI to use only what the cited feats say, and letting the player see the cited feats under `Ver mais`. Also: one without a feat that meets the floor (`MEDAL_MIN_TIER` with a non-empty `cost`, `LEGACY_MIN_TIER`); honors for the same character beyond the per-character cap (RC `MAX_MEDALS_PER_CHARACTER_PER_CHAPTER`, default 3, and one legacy per character per act; keep the ones backed by the highest-tier feats); a feat id cited by more than one medal (keep the medal with the highest-tier feat, drop the later ones); anything over `MAX_MEDALS_PER_CHAPTER` or `MAX_TITLES_PER_ACT`. **Display order comes from the ledger score** (no special treatment for the protagonist), never from the AI's order.
- **Medal vs legacy (kept distinct on purpose):** a medal answers *which deeds of this chapter deserve to be remembered* (a moment, one deed per medal; floor `MEDAL_MIN_TIER` = tier 3 with a paid cost; a short name and a reason) while a legacy answers *what did they change in the story of this act* (an arc; floor `LEGACY_MIN_TIER` = tier 4 with a persistent change; a title and a description, the legend as the world tells it). The act-close call also receives the act's continuity summary, so a legacy can go to someone with **no medal** whose influence only shows across chapters (the mentor behind the scenes), and a character with many medals may get none. The instruction says a legacy is **not a summary of the medals**. The same feat may back both, but the text changes role: the medal says what was done, the legacy says what it changed. A character with several legacies (one per act) shows the latest as the sheet's title and the rest in the honors list; tapping the legacy emblem opens the legacy sheet, which shows **all** of the character's legacies in a pager (swipe or tap the sparks), the same as the island.
- **Cost shortcut:** skip the call when the chapter has no feat at or above `MEDAL_MIN_TIER` (nothing could qualify). This only saves a call; it never decides who wins.
- **Output, medal:** `{ characterId, name, emoji, reason, featRefs[] }`: a short name, one emoji and a one-line reason.
- **What decides the medal icon:** the AI picks the `emoji` from the feat (same pattern as `GeneratedRelationshipUpdate.emoji` and the wiki/location `emojiTag`, and the same `Text` rendering the ChatBubble uses for relations). The *look* is code: a medal frame styled from the genre tokens, with the emoji inside. Upgrading the medals later means upgrading the frame, never the AI contract. If emojis drift off-theme, add an optional RC allow-list per genre that the blueprint must pick from.
- **Output, title (legacy):** `{ characterId, title, description, featRefs[] }`. `posthumous` is derived from `Character.status == DEAD`, not returned by the AI. The `description` is a short epitaph-like line in the saga's own voice, the character's legend as the world would tell it
  (cyberpunk, a character who died defying the megacorp: "died defying the giants of Arasaka; the dreams of those he loved were the only thing that mattered"). It is the line shown under the title on the sheet. A character who died gets it in the past tense (posthumous legacy); a living one gets the same register, forward-looking.
- Title and description must anchor in real feats (`featRefs`) and respect the saga's theme; never hardcoded lists. UI styling (frame, accent, badge shape) comes from the genre tokens, not from the AI.
- With only 3 acts per saga, titles are rare by design: `MAX_TITLES_PER_ACT` of 1-2, so a saga has at most a handful. Act 3 closes the saga, so its titles double as the final recognition of who mattered.
- Hooks: chapter close next to `chapter_synthesis_blueprint`; act close next to `act_conclusion_blueprint`.

## Power directive in the reply prompt

Not raw numbers. Code builds a short block for **only the characters in the scene** and injects it into `reply_generation_blueprint` args:

```
POWER_CONTEXT: Player Lv30 (trained) · Thug Lv15 (trained) · Warlord Lv85 (legendary)
Gap +15 = clear advantage. Narrate it as an advantage; no contrived obstacles.
```

- Gap bands (even / clear / overwhelming) and their sentences live in RC (`POWER_GAP_BANDS`); the labels in parentheses come from `LEVEL_BANDS`.
- The blueprint rule `POWER_CONTEXT_IS_BINDING` says the gap decides contests of the dimension at stake (combat, skill, authority); it does not decide emotional scenes.
- Candidates for the same block later: `saga_input_suggestions_blueprint` (do not suggest absurd options), live conversation.

## Character status (new sagas only, gated by `Saga.progressionEnabled`)

Until now a character's situation (alive, dead, gone) could only be read from the generated event text. Make it explicit.

- `CharacterStatus`: `ACTIVE`, `ABSENT` (alive, away from the scene, reachable), `MISSING`, `DEAD`. Nuance goes in `statusNote` ("jailed in the North Tower", "travelling north"), not in more enum values: a jailed character can still appear in a scene, so it stays `ACTIVE`.
- **Written by the Unified call**, inside `CharacterUpdates` next to knowledge/relationships/nicknames: new fields `status`, `statusNote`, `statusReason`. It is a world fact that changes per event, so it belongs there and not in the feat evaluator. Because Unified runs first, the evaluator already sees the updated status.
- **Transitions need a `statusReason`** (short, persisted with `statusTimelineId`). A wrong `DEAD` makes the character vanish from replies, so the options menu lets the player correct the status (`Alterar situação`). `DEAD → ACTIVE` is allowed only with a reason (spirit, resurrection, mistaken report).
- **Reply prompt:** each character in the context carries `status` (+ `statusNote`), with a blueprint rule `STATUS_GATES_PRESENCE`: a `DEAD` character only returns as flashback, spirit or memory; `MISSING`/`ABSENT` do not just walk into a scene without a reason. Also helps pick who may speak or be suggested.
- **No guard in the evaluator:** status is passed as information (a `DEAD` character who acts is a spirit/flashback and may still earn a feat). Participation, not status, decides who is evaluated.
- **Honors:** `posthumous` is derived in code from `status == DEAD` at the act close, not returned by the AI.
- **Old sagas stay closed (decided):** `status` is `null` and never filled, the Unified status fields and the reply-prompt status rule are skipped, and the UI hides everything. Behavior of existing sagas does not change.

## Review when a generation failed

The three calls (feat evaluation per event, honors per chapter, legacy per act) can fail. Each item carries a boolean (`experienceGenerated`, `honorsGenerated`, `legacyGenerated`) that says whether its **last generation succeeded**; an empty result is a success and does not leave it false.

- **Detection:** when the player opens a saga with progression enabled and any flag is false (ignoring the event that is still being processed), show a **sheet** with a clear message: some points of the story need a review to generate their experience (levels, medals, legacy), with `Revisar agora` and `Depois`.
- **Review run:** runs the pending calls in dependency order (events first, then chapter honors, then act legacies, since honors read the feats). Progress shows in the island as persistent work (a `GlobalShellEffect` with priority `PersistentWork`, like the generation ones), so it never fights a transient announcement.
- **No flood of announcements:** a review never replays announcements event by event. It marks everything as announced and shows at most one merged `Novo nível` if any level rose.
- **Regenerating an event or chapter** sets its flag back to false and reruns the same calls, so honors and levels follow the new text; announced flags already seen are not reset.
- This replaces the earlier idea of sweeping unevaluated events silently on the next successful event.

## UI (kept deliberately small)

- Character sheet: level pill on its own line just above the occupation (header otherwise unchanged), a **legacy emblem** above the name: a glossy faceted star in two layers, in the saga's primary tones, with the genre's own icon (`genre.icon`, the same drawable `GenreChoiceCard` uses) embossed in the center and no ribbon. It carries about five **animated sparkles** modeled on `StarryTextPlaceholder` (4-point stars with a blurred glow, fade in/out in ~1.5-2.4 s cycles, breathing scale, repositioned around the emblem each time they go invisible; note that composable lives in the monorepo's android module, not in this checkout). The icon sits inside the inner layer with generous padding. It reflects a shimmer about every 10 s and levitates gently (a few dp up and down with a soft shadow below); tapping it opens a bottom sheet that explains the legacy (title, description, the feats of the act that earned it) where the emblem spins fully in 3D (graphicsLayer `rotationY` with `cameraDistance`, a few stacked layers for thickness), then Honras (title + description in the glass card, medals in a grouped list) and the **feat log** (title, `changed`, `cost`, XP). The log is the explanation of the number.
- **Level is visible on purpose** (decided): it tells the player how dangerous a threat is. **Shown once per surface, never twice:** chat messages show `Lv N` right after the name and nothing on the avatar; the character list (no text beside the avatar) puts a small chip on the avatar's top-right corner; the sheet shows the pill with the occupation.
- **Legacy on the avatar:** glow plus a light shimmer that runs around the existing ring about every 10 s (idle in between). No screen frame, no frame on the detail screen. A memorial legacy is silver, no shimmer, desaturated photo.
- **Medals:** no counter anywhere. In the character list the **latest medal sits below the avatar**, right after the icon and before the name, never over the photo (the bottom-center slot over the avatar stays with the relation emoji in the chat). Full medals live in Honras. Not shown in chat.
- **Medal look (decided):** a glossy **coin**, the same visual language as the legacy emblem but simpler so the two are never confused. Legacy = 12-point star, two layers, genre icon embossed, ~5 sparkles, shimmer, levitation, 3D spin in the sheet. Prestige medal = coin with a light rim, a darker inner ring, a central disc and a visible thickness at the bottom, two soft gloss streaks, a soft glow and **one** sparkle; the AI's emoji is **engraved** in the disc as a silhouette in a dark tone of the saga's primary color with a faint light edge below, no other motion. **Nothing decides the shape: it is always a coin**, so the earlier kind-to-shape table is gone and the honors call's only visual output stays the `emoji`. Colors come from the saga's primary color (rim/disc light-to-mid gradient, ring darker, edge darkest). Emoji silhouettes lose inner detail: simple glyphs (bolt, drop, shield, magnifier) read well, busy ones can blur, so favor an optional RC allow-list of glyph-like emojis per genre if the AI drifts. Native: draw the coin on a canvas, the emoji `Text` tinted via a color filter; iOS: the same as a mask.
- **Feat log shows only the event and its XP** (decided). Tiers are internal and never displayed. `changed`/`cost` stay available on tap (collapsed by default) so a 0 XP or large XP event can still be explained without cluttering the list.
- Announcements go through the top island (see below): a light pill per event for level-ups, and a reveal milestone of their own for medals (after the chapter) and legacy (after the act). The detail of XP and honors lives in the story's own screens (timeline, chapter, act) and on the character sheet; the level number is the only permanent chrome.

## Level-up, medal and legacy announcements (reuse the top island)

The top island has two existing paths: `SagaMilestone` -> `NarrativeMilestoneIslandContent` (heavy reveal, intrusive, auto-expands: `NewEvent`, `ChapterFinished`, `ActFinished`) and `GlobalShellEffect` -> `NotificationIslandContent` (light transient pill: `NewMessage`, `NewChapter`, `NewCharacter`, `ReviewReady`, `BookReady`), routed by `GlobalShellService`.

- **Level-up is a `GlobalShellEffect`, not a milestone.** A new `CharacterLevelUpEffect` (priority `Transient`): compact pill with the character's circular avatar (same as `NewCharacterEffect`) and `Maya · Lv 35`; tap expands to the feat title, its XP and a "ver mais" action (deep link to the **event in the timeline screen**, where each character's reply shows its XP and the feat behind it). Level-ups can happen almost every event, so a takeover reveal each time would wear the player out.
- **Look (island style from the app's own screenshots: black card, large corners, genre-colored border and glow):** compact = a centered capsule sized to its content (about 58% of the width, like the image-generation one), the character's circular avatar in place of the genre icon + `Name · Lv N` + an up arrow in the trailing slot rendered as theme-gradient text with a glow, **no background chip**; expanded (tap) = the new level as a big number with `subiu de nível` right below it, the feat row with its XP, a primary action `Ver mais` and a quiet `Fechar`; merged (more than one character) = a **generic** header, no avatars and nobody highlighted: the spark + `Novo nível` + the up arrow, with one row per character (`Lv 35` with an up arrow, the feat title; no `from -> to`). Use the theme's light text color: the image-generation island's label is dim wine on black today and hard to read.
- **No title in the level-up card (decided).** Level-ups happen per event, medals at chapter close and the legacy title at act close: three different generation steps with nothing tying a new level to a new title (a title per level would not match the feats that paid the XP). The power-scale anchors' labels ("veterana das ruas") stay a prompt-side concept for the power directive and are not shown as a title anywhere in the UI for now, so they are never confused with the legacy title. At chapter close the announcement only says which medals were granted.
- **Rejected:** an overlay over the chat text (a parallel render path outside the island, and it hides what is being read) and an inline line in the chat list (messages feed the AI context and it breaks the diegesis).
- **Rules specific to this effect:**
  - `shouldSuppress` only while the user is on **that character's detail**. Unlike `NewMessage`/`NewChapter`, it must NOT hide when the user is in the chat, because the chat is exactly where it has to be seen.
  - **One effect per event** that merges every level-up of that event (listed by score, no special treatment for the protagonist; cap in RC). `GlobalShellService` keeps only the latest transient while persistent work (image generation) is active, so separate effects could overwrite each other.
  - **No system notification.** For a transient in background the service calls `deliverSystemNotification`; add an effect flag so this one is dropped instead. The idempotent flag below announces it later.
- **Medals and legacy are reveal milestones of their own, right after the milestone that closes the chapter/act**, because they are chapter/act-sized moments, the milestone is the island's reveal surface and each needs its own compact header:
  - **Chapter close:** the medals are a new `SagaMilestone` right after `ChapterFinished` (the same pattern as the legacy after `ActFinished`), with its own header `Medalha conquistada` / `Medalhas conquistadas`; one card per character in the body. In the compact header (same layout as the level-up capsule): the character's circular avatar on the left, `Name · nova medalha` in the middle and the latest medal's coin in the trailing slot on the right; for two or more, `Name · N medalhas` with the latest coin. Nothing about levels or titles here.
  - **Several at once:** several medals (different characters) -> the compact header is **generic**, no avatars and nobody highlighted (the protagonist gets no special treatment): the spark + `Medalhas conquistadas` + a medal coin in the trailing slot; the expanded body shows **one card per character** (score order, no special treatment for the protagonist): the avatar with the name below it, the character's **latest medal** (coin, name, one-line reason) and, at the right next to the chevron, only a `+N` counter in plain text (no gradient, so it does not compete) for the remaining ones (no count label above it, to keep the island light). Tapping a card opens that character's detail screen (their honors). A single character with several medals reads `Name · N medalhas` in the compact header, with the coin of the highest-tier one. `Ver mais` is always present and opens the chapter at its medals section (see the destinations below). Several legacies (different characters) -> the compact header (the legacy's own milestone) shows `Legados conquistados`; the expanded body is a **pager, one legacy per page** with the spinning emblem, the character's avatar with the name below it, a horizontal swipe between pages (the sparks are tappable too; the swipe hint hides on the last page) and, as the page indicator, the app's `ic_spark` itself (the current page's spark lit in the theme gradient with a glow, the others dimmed), in score order. Medals and legacy never share a body: the medals milestone comes right after `ChapterFinished` and the legacy milestone right after `ActFinished`; when the last chapter closes the act they are consecutive, chapter first.
  - **Act close:** the legacy is its **own reveal milestone right after `ActFinished`** (a new `SagaMilestone` type), so it has its own compact header: `Legado conquistado`, or `Legados conquistados` in the plural (generic, nobody highlighted). It auto-expands like the other reveals (`autoExpandAfterMs`): the emblem spinning in 3D, the **character's avatar right under the emblem with the name below it** (a vertical stack; the island is allowed to grow to fit) (so who earned it reads at a glance; a deceased character's avatar takes the silver memorial treatment), the title and the description, then `Ver mais`. No `Legado · Ato N` label: the header already says what it is and the card on the character's detail screen explains the act. In the header (the same row in the compact and the expanded form), the leading indicator is the spark and the trailing slot is a **mini 3D legacy badge**: the legacy emblem itself in miniature (the genre icon, e.g. the red dragon in Fantasy, sits at its center) with a gentle 3D sway and a soft glow. It is the counterpart of the medal's coin: the medals milestone shows a coin there, the legacy milestone shows the badge. The compact form of `Legado conquistado` and `Legados conquistados` is identical.
  - The honors call runs after the chapter/act synthesis. Its milestone is published **only when the call returns at least one valid honor**; an empty result or a failure (wrapped in `RequestResult`, retried later) publishes nothing, and it never delays `ChapterFinished`/`ActFinished`. Each `CharacterHonor` carries an `announced` flag so that, if the player left before the call finished, it is announced on the next foreground instead of being lost.
- **Island styling (decided):** the leading indicator everywhere is the app's own `ic_spark` (its path converted 1:1 to SVG for the mockup), filled with the theme gradient with a soft glow and a slow pulse instead of a plain dot; the level number and the legacy title use the theme gradient with a glow of the theme color; trailing indicators are gradient text/icons without a background; the action button is flat, in the theme's primary color only (no border, gradient or glow), so it never competes with the medals and emblems.
- **Where the details live (destinations of `Ver mais`, decided):** the XP and honors detail is shown in the story's own screens, so `Ver mais` always lands on the exact event, chapter or act:
  - **Level-up -> `TimeLineContent` at that event.** `TimelineThreadCard` already lists per-character replies (`TimelineReplyItem`, from the character events); each reply gains its XP and, on tap, the feat's `changed`/`cost`, and shows `Lv N` with an up arrow when the level changed (no `from -> to`). `TimeLineContent` today takes only `sagaId`, `title` and `subtitle`, so it needs an `eventId` to scroll to and highlight that card.
  - **Medals -> `ChapterView` at that chapter.** `ChaptersGalleryContent` renders one `ChapterContentView` per chapter; add a medals section after the chapter content (one card per character, like the island). Needs a `chapterId` to scroll to.
  - **Legacy -> the act's `ActComponent`.** Add a legacy section after the act text and emotional review. Needs an `actId` anchor.
  - **A character card inside any island body -> that character's detail screen** (honors and the feat log).
- **Island arbitration (read in `MainActivity`):** the top slot is chosen by priority: image generation > book generation > chat generation > a `GlobalShellEffect` notification > `chatTopIsland` (where milestones and the objective live, lowest). A transient therefore **pre-empts an open milestone** and resets its expansion (the island key changes). So the level-up effect must not be posted immediately: hold it while a generation or a milestone island is active and release it when the slot is free (a small gate in the announcer, reading `chatIslandService.top` and the generation states). Medals and legacy are milestones (the lowest-priority path), so they do not fight transients, but two milestones can queue up at a chapter close (`ChapterFinished`, then the medals one): they must be published one after the other, the second only when the first is dismissed.
- **Detection is derived and idempotent:** the level after event N comes from the ledger (`baseLevel` + XP up to N). Announce when `level(N) > level(N-1)` and `Timeline.progressionAnnounced` is false; set it true once the effect has been shown or expanded. If the player was away, the next foreground event announces the pending ones merged, oldest first.
- **Text is deterministic** (names, levels, feat titles), no AI call. The user-level "notifications" setting also silences it, as with the other transients.
- Old sagas: nothing is announced.

## Decisions taken after review

- **`Abilities` -> `skills` (decided):** for new sagas the two free-text fields are replaced by `skills: List<String>`. `character_generation_blueprint` outputs `skills[]` directly, the feat evaluator appends `newSkills` (deduped, capped by `MAX_SKILLS`), and `CharacterAbilitiesSection` shows them as chips. `uniqueOrSignatureTalents` is dropped for new sagas; the old columns stay only for old sagas. Check the `VoicePrompts` exclusion list (it already skips `abilities`; skip `skills` too).
- **Translations and backup:** nothing special. Strings go to the resources of each locale as usual, and the backup follows the database.
- **No new onboarding (decided):** a one-time explainer inside the first level-up island ("what is this and where do I read the details"), text in string resources, a `seen` flag in the preferences. Remote Config only keeps the existing feature flag and kill switch.
- **Setting to hide experience data (decided):** a simple toggle in the settings, on by default and stored with the other user settings like the notifications one. Off hides the level pill and chip, the island announcements, the feat log and the honors; the power directive keeps working underneath.

## Sagas in progress (decided 2026-10-08)

`progressionEnabled` is true only for sagas created after release. Existing sagas stay `false`, so nothing changes for them and the migration is schema-only (additive, nullable or defaulted columns, new tables; no data rewritten). The one exception is an **opt-in debug backfill** in `LoreDebugViewModel`, used on the developer's own running saga and as the phase 0 calibration set. It is never automatic and never offered to other old sagas (cost, and old sagas stay closed).

Shape (same molde as `fixStory()`: filter what is missing, run in order, `currentFixItem/fixItemsCount` progress):

1. **Placement:** per character, `baseLevel` + `skills[]` from the backstory (which describes the origin, so the replayed XP does not count the past twice) and the roster.
2. **Event replay:** completed events (`isComplete(rules)`) in chronological order through `character_feat_evaluation`; same caps and decay as live. Feats are keyed by `(characterId, timelineId, ordinal)`, so a failed run resumes without duplicating.
3. **Honors:** closed chapters through the medals blueprint, closed acts through the legacy blueprint.
4. **Status:** one final pass so characters who died earlier are not `ACTIVE`.
5. **Silence:** everything is written with `announced = true` / `progressionAnnounced = true`; no islands or notifications for backfilled history.
6. Then `progressionEnabled = true`; the open event is evaluated by the normal flow when it closes.

Level is derived from `baseLevel` + `SUM(xp)`, so changing `TIER_XP`, the curve or the caps in RC recalculates instantly with no AI call. Only a prompt change needs a re-run, hence a **"reset progression for this saga"** action (delete feats and honors, clear flags). Back up the database before the first real run. Caveat: the judgement runs on the events' text, not the original chat, so tiers will differ slightly from a saga born with the feature.

## Risks and open items

- **Evaluator quality is the whole product.** If tiers feel arbitrary, nothing else matters. Phase 0 exists for this.
- **Cost:** +1 call per event (small prompt) and +1 per chapter close and per act close, skipped when no feat reaches the floor. Measure in phase 0.
- **Failed evaluations:** handled by the generation flags and the review sheet (see "Review when a generation failed").
- **Death by sacrifice (decided):** no code guard and no death tracking. A character who left the story is simply not a participant of later events, so the evaluator never sees them and no feats accrue; a spirit that truly acts does count. The title and description are still granted at the act close. With `Character.status` (see "Character status") the honors flow reads `DEAD` to write a past-tense description and show the "in memory" mark.
- **Curve rebalance:** XP is frozen per feat, so a new curve changes pace, not the log. Levels on existing new-saga characters may shift; acceptable.
- **KMP/iOS parity:** later, after Android is validated end to end. Keep the curve, tier table, decay and caps in portable pure Kotlin so the move is cheap.
- **Level in the evaluator's prompt** can bias the judge; it only receives levels for risk calibration and the code guards clamp inflation.
